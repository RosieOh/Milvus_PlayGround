Side Project Plan

임베딩 모델을 바꾸는 동안에도 검색은 멈추지 않는다

RAG 서비스에서 임베딩 모델 교체는 언젠가가 아니라 반드시 일어난다. 그리고 그 순간 전량 재색인이 필요하다. VecShift는 이 재색인을 다운타임 없이, 품질 회귀를 사전에 차단하면서, 실패 시 10초 안에 되돌릴 수 있게 만드는 운영 하네스다.

01

문제 정의

왜 이 문제를 고르는가.

임베딩 교체는 상수다

더 나은 다국어 모델이 나오거나, 추론 비용을 줄여야 하거나, 차원을 1024에서 768로 낮춰 메모리를 확보해야 할 때 — 임베딩 모델은 바뀐다. 모델이 바뀌면 벡터 공간 자체가 달라지므로 기존 인덱스는 전부 무효가 된다. 부분 업데이트가 불가능하고, 전량 재계산과 재색인만이 답이다.

그런데 검색은 24/7 떠 있어야 한다

현장에서 실제로 벌어지는 일은 대개 셋 중 하나다.

  • 새벽 점검 창을 잡고 내린다 — 다운타임이 발생하고, 데이터가 커질수록 창이 부족해진다.
  • 컬렉션 두 개를 수동으로 굴린다 — 전환 시점에 유입된 쓰기가 유실되고, 되돌릴 절차가 없다.
  • 검증 없이 갈아끼운다 — recall 회귀를 배포 후 사용자 불만으로 발견한다.
공백 벡터 DB 문서도, LangChain·LlamaIndex 같은 프레임워크 문서도 "인덱스를 만드는 법"은 상세히 다루지만 "이미 서빙 중인 인덱스를 교체하는 법"에 대한 챕터는 없다. 한국어 자료는 사실상 전무하다. 이 공백이 이 프로젝트의 존재 이유다.

왜 Milvus인가

Milvus 3.0이 이 문제를 풀 재료를 최근에야 갖췄다. Snapshot(파일 복사 없는 시점 고정 뷰), 온라인 스키마 진화(서빙 중 컬럼 추가·백필), alias(무중단 전환 포인트), 그리고 스토리지-컴퓨트 분리 구조 덕분에 v2 빌드가 v1 서빙의 CPU·메모리를 잠식하지 않는다. 같은 일을 pgvector나 단일 프로세스형 엔진에서 하려면 훨씬 지저분해진다.

02

목표와 비목표

4주 안에 완주하기 위해, 안 할 것을 먼저 못 박는다.

In Scope

  • 인덱스 구성 탐색 자동화 — 인덱스·양자화·파라미터·필터 비율을 축으로 스윕하고 recall/QPS/메모리 파레토 곡선을 뽑는다.
  • 무중단 재색인 파이프라인 — 스냅샷 → 격리 빌드 → 쓰기 따라잡기 → 섀도우 검증 → alias 스왑 → 롤백.
  • 정량 게이트 — 기준 미달이면 스왑을 자동으로 거부한다. 사람이 판단하지 않는다.
  • 재현 패키징 — docker compose up 후 make bench / make shift 두 줄로 끝난다.
  • 관측성 — Milvus Prometheus 메트릭 기반 Grafana 대시보드 1장.

Out of Scope

  • Distributed(K8s) 모드 — Standalone까지만. 운영 복잡도가 4주를 삼킨다.
  • 프로덕션 SLA·멀티리전·HA — 검증 대상이 아니다.
  • 임베딩 모델 학습·파인튜닝 — 공개 모델만 사용한다.
  • Milvus 소스 포크·패치 — 클라이언트 레이어에서만 푼다.
  • 웹 UI 대시보드 — Grafana와 정적 리포트로 대체한다.
  • RAG 애플리케이션 자체 — 검색 계층까지. 생성은 다루지 않는다.
스코프 규율 W4는 코딩 금지 주간이다. 리포트·README·블로그만 쓴다. 사이드프로젝트가 포트폴리오가 되지 못하는 가장 흔한 원인은 기능 부족이 아니라 "설명이 없는 코드"로 끝나는 것이다.
03

성공 기준

전부 자동 측정 가능한 숫자로만 정의한다. 주관적 기준은 넣지 않는다.

지표목표측정 방법
재색인 중 다운타임 0 s 부하 생성기가 전 구간 연속 질의, 5xx·타임아웃·빈 응답 카운트
재색인 중 p99 증가 ≤ +15 % 유휴 베이스라인 대비, 빌드 구간 전체의 p99
recall@10 회귀 차단 −0.01 초과 시 중단 골든셋 500 질의, FLAT 브루트포스를 정답으로 사용
alias 스왑 소요 ≤ 5 s 스왑 명령 → 신규 결과 최초 관측까지
롤백 소요 ≤ 10 s 장애 판정 → v1 결과 복귀 확인까지
1.2 M 벡터 전량 재색인 ≤ 30 min 임베딩 캐시 적중 기준, 인덱스 빌드 완료까지
벤치 재현성 CV ≤ 5 % 동일 설정 3회 반복 QPS의 변동계수
쓰기 유실 0 건 전환 구간 삽입분을 v2에서 전수 조회
정직한 프레이밍 노트북 단일 인스턴스 벤치라서 절대 수치는 의미가 약하다. 모든 결과는 "동일 하드웨어·동일 데이터에서의 상대 비교"로만 서술한다. "3,200 QPS"가 아니라 "같은 조건에서 IVF 대비 2.3배"가 이 프로젝트의 문장 형식이다.
04

시스템 설계

v1 서빙 레인과 v2 빌드 레인을 물리적으로 분리하고, 게이트만이 둘을 잇는다.

구성 요소

컴포넌트레인책임

쓰기 따라잡기 전략

스냅샷 시점 t₀ 이후 유입된 쓰기를 v2가 놓치면 데이터가 갈린다. 두 전략을 구현해 비교한다.

  • Dual-write — 재색인 구간 동안 애플리케이션이 v1·v2에 동시 기록. 단순하지만 애플리케이션 변경이 필요하다.
  • Delta backfill — 소스의 updated_at > t₀ 델타를 스왑 직전에 재생. 애플리케이션 무변경이지만 마지막 델타 구간에 짧은 지연이 남는다.

어느 쪽이 더 나은지를 측정해서 결론 내는 것 자체가 산출물이다.

05

기능 명세

모듈 두 개. M1이 M2의 판정 근거를 만든다.

M1 · Index Pareto Lab

"이 데이터, 이 SLO에서는 이 인덱스 설정" 을 근거와 함께 답하는 스윕 러너. 일반론 표가 아니라 내 데이터에서의 측정값을 만든다.

축값
인덱스HNSW · IVF_FLAT · IVF_SQ8 · IVF_PQ · DiskANN · FLAT
파라미터HNSW M/ef, IVF nlist/nprobe
양자화·refinernone · SQ8 · PQ + refine 배수 1/3/5
필터 비율0 · 50 · 85 · 95 · 99 %
mmapon / off

수집 지표: recall@10 · QPS · p50/p95/p99 · 인덱스 빌드 시간 · RSS · 인덱스 파일 크기.

출력: pareto.json + recall–QPS 파레토 곡선(필터 비율별 계열) + "p99 ≤ 50 ms & recall ≥ 0.95" 같은 SLO를 넣으면 통과 설정을 추려주는 CLI.

차별점 기존 벤치 도구가 약한 지점이 필터 비율 축이다. 실제 RAG는 거의 항상 메타데이터 필터와 함께 검색하는데, 필터 비율이 85 %를 넘는 순간 그래프 인덱스와 IVF의 우열이 뒤집힌다. 이 뒤집힘 지점을 내 데이터에서 찾아 제시하는 것이 M1의 핵심 결과물이다.

10

확장 로드맵

4주를 완주한 뒤에 손대는 것들. 지금은 건드리지 않는다.

  • External Collection 경로 — Iceberg·Parquet에 있는 데이터를 복사 없이 인덱싱하는 "ETL 없는 재색인". 희소성이 가장 높지만 문서가 가장 부족하다.
  • Multi-vector 비교 — StructArray 위에서 TokenANN / Muvera / Lemur 세 전략의 비용·정확도 곡선.
  • Sparse SINDI 검증 — 한국어 학습 sparse 임베딩에서 "MaxScore 대비 최대 10배" 주장을 실측.
  • 멀티테넌시 — partition key 기반 테넌트별 재색인. 전체가 아니라 일부 테넌트만 교체하는 시나리오.
  • 비용 모델 — 인덱스 설정 → 메모리 → 인스턴스 타입 → 월 비용. 엔지니어링을 돈으로 번역하는 마지막 한 칸.
